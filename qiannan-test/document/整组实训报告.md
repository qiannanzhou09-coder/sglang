# 整组实训报告：SGLang 长会话推理服务优化

## 一、实训目标

- 本次实训针对 SGLang 长会话推理服务做优化。
- workload 特点是多 session、多轮对话、prompt 前缀复用明显，但随着会话变长，KV cache 压力会持续增加。
- 优化目标：
  - 提高吞吐；
  - 保持 prefix cache 命中；
  - 降低 TTFT 和尾延迟；
  - 避免长时间运行后 cache miss 增多、吞吐坍塌；
  - 尽量降低模型和 KV cache 显存占用。

> 截图占位：数据集长度 / session 分布 / offered QPS 图

## 二、测试基线

- 使用纯 TP8 作为 baseline。
- T1 数据集用于观察 cache/router 是否正常，T6 数据集用于接近官方分布的小规模对比。
- baseline 结果：
  - T1：`cache_hit_rate=97.95%`，`output_throughput=799.7 tok/s`。
  - T6：`avg_session_time=165.65s`，`cache_hit_rate=96.72%`，`output_throughput=596.8 tok/s`。
- 结论：
  - TP8 baseline 很稳，cache 命中高。
  - 后续所有优化都以它作为对比基准。

## 三、优化一：初步并行策略调整

### 1. DPA TP8 DP8 + cache-aware router

- 尝试内容：
  - 开启 `--enable-dp-attention`。
  - 使用 `tp_size=8`、`dp_size=8`。
  - client 通过 cache-aware router 访问服务。
- 结果：
  - T1 cache hit 仍然较高，但吞吐从 TP8 baseline 的 `799.7 tok/s` 降到 `286.6 tok/s`。
  - 观察到 cache-aware router 把请求集中到少数 DP rank，甚至单 rank 过热，其他 rank 空闲。
- 是否有效：
  - **整体无效。**
- 原因：
  - router 过度追求 cache locality，虽然保住了 cache hit，但破坏了 DP 负载均衡。
  - 单个 rank 排队后，整体吞吐下降。

> 截图占位：DP8 cache-aware router 单 rank 过热 / queue 图

### 2. DPA 参数补偿

- 尝试内容：
  - 设置 `CHUNKED_PREFILL_SIZE=65536`。
  - 设置 `SCHEDULE_CONSERVATIVENESS=3.33`。
- 结果：
  - T1 吞吐从 `286.6 tok/s` 提升到 `375.5 tok/s`。
  - 但仍低于 TP8 baseline。
- 是否有效：
  - **部分有效。**
- 原因：
  - 调度参数改善了 DPA 默认表现。
  - 但核心问题仍是 router 负载倾斜，所以提升有限。

### 3. no-router 对照实验

- 尝试内容：
  - DPA 直接打 SGLang，不经过 cache-aware router。
- 结果：
  - DP rank 负载明显更均衡。
  - 但同一 session 可能被分散到不同 rank，cache hit 下降。
- 是否有效：
  - **作为诊断有效，不适合作为最终方案。**
- 原因：
  - 证明 DPA 本身不是唯一瓶颈，router 策略才是导致 DP8 慢的重要原因。
  - 但完全不用 router 会破坏多轮会话 cache 复用。

### 4. length-aware proxy

- 尝试内容：
  - 在 router 前增加 length-aware proxy。
  - 短请求直接打 SGLang，长请求走 cache-aware router。
- 结果：
  - 特殊场景下能缓解一部分负载倾斜。
  - 但 T6 clean 上 `avg_session_time=419.66s`，比原 router 的 `346.29s` 更差。
- 是否有效：
  - **收益有限。**
- 原因：
  - 长度信息只能粗略区分请求，不能真正解决 cache locality 和 load balance 的冲突。

### 5. DP size 从 8 调整到 2

- 尝试内容：
  - 改为 `TP8 + DP2 DPA + cache-aware router`。
- 结果：
  - T6 上 `avg_session_time=246.73s`，`cache_hit_rate=96.52%`，`output_throughput=551.5 tok/s`。
  - 比 DP8 明显更稳。
- 是否有效：
  - **有效。**
- 原因：
  - DP2 减少了 KV cache 被切碎的程度。
  - DP rank 数量更少，router 更容易兼顾 cache 和负载。
  - 虽然小规模 T6 仍慢于 TP8 baseline，但在完整 workload 高并发场景下更有继续优化空间。

## 四、优化二：参数调优

### 1. 关闭投机解码

- 尝试内容：
  - 设置 `SPECULATIVE_ALGO=NONE`。
- 结果：
  - 修正了实验中的干扰因素。
  - 之前开启投机解码时，默认最大运行请求数会变小，导致结果被误判。
- 是否有效：
  - **有效，而且是必要修正。**
- 原因：
  - 关闭后实验结果更稳定，便于判断 DPA、router、cache 的真实效果。

### 2. 提高 `MAX_RUNNING_REQUESTS`

- 尝试内容：
  - 设置 `MAX_RUNNING_REQUESTS=640`。
- 结果：
  - 完整 workload 前期吞吐可以提升到约 `1700-1900 tok/s`。
  - 但后期出现 cache hit 下降、TTFT p99 暴涨、输出吞吐下降。
- 是否有效：
  - **短期有效，长期无效。**
- 原因：
  - 更高并发能提高前期 GPU 利用率。
  - 但长会话不断增长后，活跃 session 的 KV working set 过大，会挤爆 cache，导致大量 uncached prefill。

> 截图占位：完整 workload 中后期 cache hit 下降 / output throughput 下降图

### 3. `ENABLE_DP_LM_HEAD`

- 尝试内容：
  - 开启 `ENABLE_DP_LM_HEAD=1`。
- 结果：
  - 指标变化不明显。
- 是否有效：
  - **暂未体现明显效果。**
- 原因：
  - 当前主要瓶颈不在 LM head 通信，而在 KV cache、prefill 和长会话调度。

### 4. 调整 `MEM_FRACTION_STATIC`

- 尝试内容：
  - 测试 `MEM_FRACTION_STATIC=0.9`、`0.92`、`0.95`。
- 结果：
  - `0.92` 比 `0.9` 更好。
  - `0.95` OOM。
- 是否有效：
  - **有效，但有边界。**
- 原因：
  - 增大可用于 KV cache 的显存，可以缓解长上下文 cache 压力。
  - 但显存不能无限挤，过高会导致模型启动或运行 OOM。

### 5. 启用 HiCache

- 尝试内容：
  - 设置：
    - `ENABLE_HICACHE=1`
    - `HICACHE_RATIO=2`
    - `HICACHE_IO_BACKEND=kernel`
    - `HICACHE_STORAGE_PREFETCH_POLICY=wait_complete`
    - `HICACHE_WRITE_POLICY=write_through`
- 结果：
  - HiCache 启用后能缓解长会话 KV cache 压力。
  - 过程中发现并修复了 SGLang FlashInfer metadata buffer 与 CUDA graph padded batch size 不一致的问题。
- 是否有效：
  - **有效。**
- 原因：
  - 完整 workload 的后期瓶颈是长上下文 KV cache 容量不足。
  - HiCache 可以把部分 KV 压力从 GPU cache 中释放出来，提高长时间运行稳定性。

## 五、优化三：模型量化与剪枝

### 1. REAP text-only 剪枝模型

- 尝试内容：
  - 参考 REAP 论文做 MoE expert 剪枝。
  - 使用 `PRUNE_MODE=reap_text_only`。
  - 删除部分 expert，并去掉当前文本 workload 不需要的 visual 相关权重。
- 结果：
  - 显存占用从约 `119GB` 降到约 `96GB`。
- 是否有效：
  - **对显存有效。**
- 原因：
  - 剪枝减少了 MoE expert 权重。
  - text-only 去掉了不参与文本推理的视觉模块。
- 仍需验证：
  - 剪枝后速度是否提升；
  - 精度是否下降；
  - 长上下文任务是否稳定。

### 2. KV FP8

- 尝试内容：
  - 计划测试 `kv_cache_dtype=fp8_e4m3`。
  - 对比 baseline、KV FP8、剪枝模型、剪枝模型 + KV FP8。
- 是否有效：
  - **待验证。**
- 原因：
  - KV FP8 理论上能减少 KV cache 显存占用。
  - 但可能影响长上下文精度，必须配合精度评测一起看。

## 六、优化四：准入控制

### 1. 发现问题：中后期 cache miss 坍塌

- 现象：
  - 完整 workload 跑到中期后，cache hit 明显下降。
  - output token throughput 一路下跌。
  - TTFT p90/p99 明显升高。
- 判断：
  - 不是请求变少导致 token usage 低。
  - 而是太多长会话同时活跃，KV working set 超出 cache 容量，导致大量请求重新 prefill。

> 截图占位：准入控制前 cache miss / TTFT p99 / throughput 坍塌图

### 2. 静态 active session 限制

- 尝试内容：
  - 设置 `MAX_ACTIVE_SESSIONS=64`。
  - 限制同一时间最多只让 64 个 session 活跃。
- 结果：
  - cache 命中后期保持较高。
  - output token throughput 更平稳。
- 是否有效：
  - **有效。**
- 原因：
  - 限制 active session 后，KV working set 变小。
  - cache 不再频繁被不同 session 的长历史冲掉。
  - 这比单纯提高并发更适合长会话 workload。

### 3. request-level in-flight 限制

- 尝试内容：
  - 在 proxy 层设置 `MAX_INFLIGHT_REQUESTS=64`。
- 是否有效：
  - **有限有效。**
- 原因：
  - 它能限制瞬时请求数，避免上游被打爆。
  - 但真正导致 cache miss 的是长期活跃 session 数，不只是瞬时 HTTP request 数。

### 4. dynamic admission

- 尝试内容：
  - 在 proxy 中加入动态准入控制。
  - 根据运行状态动态调整 active session / inflight 限制。
- 是否有效：
  - **方向有效，还需要继续调参。**
- 原因：
  - 静态 `64` 有效果，但不适合所有 workload。
  - 动态准入可以根据 cache hit、KV usage、TTFT 等指标自动调节并发。

## 七、阶段性结论

- 初步并行策略中，**DP8 DPA + cache-aware router 无效**，主要因为负载倾斜。
- **DP2 DPA 是更合理的并行方案**，在 cache 保持和负载均衡之间更稳。
- 参数调优中，**关闭投机解码、调整 KV 显存比例、启用 HiCache 有效**。
- 单纯提高 `MAX_RUNNING_REQUESTS` 只能提高前期吞吐，后期会导致 cache 坍塌，不能单独作为最终方案。
- 模型剪枝对显存有效，`119GB -> 96GB`，但速度和精度还要继续验证。
- 准入控制是完整 workload 中最关键的稳定性优化，`MAX_ACTIVE_SESSIONS=64` 已经能明显缓解 cache miss 和吞吐坍塌。

## 八、当前推荐组合

- 当前推荐继续验证的组合：
  - `TP8 + DP2 DPA`
  - `cache-aware router`
  - `SPECULATIVE_ALGO=NONE`
  - `MEM_FRACTION_STATIC=0.92`
  - `HiCache`
  - `session 级准入控制`

- 后续继续测试：
  - REAP text-only 剪枝模型；
  - KV FP8；
  - 剪枝模型 + KV FP8；
  - dynamic admission；
  - HiCache ratio 调整。
