# 整组实训报告：基于 REAP 的 MoE 模型压缩与推理服务优化

## 一、实训课题

- 本次实训围绕 **MoE 大模型压缩与推理服务优化** 展开。
- 参考方向来自论文 **“REAP THE EXPERTS: WHY PRUNING PREVAILS FOR ONE-SHOT MOE COMPRESSION”**。
- 课题核心思想：
  - MoE 模型中 routed expert 数量多，显存占用和推理部署成本较高。
  - REAP 主张在 one-shot MoE 压缩场景下，**专家剪枝比专家合并更适合生成任务**。
  - 剪枝时需要尽量保留重要 expert，删除贡献较低的 expert，从而减少模型体积和 serving 成本。

## 二、实训目标

- 将 REAP 思想接入到本地 Qwen3.5 MoE 模型压缩流程中。
- 生成可被 SGLang 加载的 pruned checkpoint。
- 在压缩模型基础上继续做推理服务优化。
- 对每个优化判断是否有效，而不是只看单个吞吐指标。

## 三、主要工作与优化效果

- **1. 接入 REAP expert 剪枝方案**
  - 做法：
    - 使用 `targeted_refusal_analysis.json` 作为剪枝计划。
    - 原模型每层有 `256` 个 routed experts。
    - 每层剪掉 `51` 个 experts，保留 `205` 个 experts。
    - 共处理 `48` 个 MoE 层，剪枝比例约为 `20%`。
  - 实现：
    - 编写/使用 `qiannan-test/tools/prune_reap_ckpt.py`。
    - 删除被剪 expert 的 `gate/up/down` 权重。
    - 重新编号保留的 experts。
    - 同步缩小 router gate 权重。
    - 修改 `config.json` 中的 `num_experts`。
  - 是否有效：
    - **有效。**
    - 已经能从 checkpoint 层面真实减少 expert 数量。
    - 这是后续降低显存和 serving 成本的基础。
    - 但最终精度仍需要通过 GSM8K、RULER 等任务继续验证。

- **2. 支持 FP8 checkpoint 的剪枝**
  - 做法：
    - 针对 FP8 模型同时处理 `.weight` 和 `.weight_scale_inv`。
    - 采用 safetensors 分片流式处理，避免一次性加载完整大模型。
  - 是否有效：
    - **有效。**
    - 方案适合大模型 checkpoint，不需要重新训练，也不需要校准。
    - 可以直接生成可部署的 FP8 pruned model。

- **3. 删除 visual tower，生成 text-only 模型**
  - 做法：
    - 在 `--strip-visual` 模式下删除 `model.visual.*`。
    - 同时移除 `vision_config` 和图像/视频 token 配置。
    - 支持 `reap_text_only`，即 expert 剪枝 + 删除视觉模块。
  - 是否有效：
    - **有效。**
    - 当前 workload 是文本推理，视觉模块不会参与计算。
    - 删除 visual tower 可以减少无关权重和加载成本。
    - 对文本任务理论上没有负面影响，但仍需做精度回归确认。

- **4. 将剪枝流程集成到启动脚本**
  - 做法：
    - 在 serving 脚本中加入 `PRUNE_MODE`。
    - 支持 `none`、`strip_visual`、`reap`、`reap_text_only` 四种模式。
    - 剪枝模型已存在时直接复用，避免重复生成。
  - 是否有效：
    - **有效。**
    - 降低了实验启动成本。
    - 让 baseline、text-only、REAP、REAP-text-only 可以用统一流程测试。

- **5. 选择 TP8 + DP2 DPA + cache-aware router 作为基础架构**
  - 做法：
    - 早期对比了纯 TP8、DP8 DPA、DP2 DPA、是否经过 router 等方案。
    - 最终 stage-1 选择 `TP8 + DP2 DPA + cache-aware router`。
    - 关闭投机解码：`SPECULATIVE_ALGO=NONE`。
    - 设置较高并发上限：`MAX_RUNNING_REQUESTS=640`。
  - 是否有效：
    - **有效，但有条件。**
    - DP8 在部分场景下会出现 DP rank 负载不均。
    - DP2 比 DP8 更稳，cache 切分和负载均衡更容易控制。
    - 该架构适合作为后续 HiCache、准入控制、剪枝模型测试的基础。

- **6. 启用 HiCache 缓解长会话 KV 压力**
  - 做法：
    - stage-2 选择：
      - `MEM_FRACTION_STATIC=0.92`
      - `ENABLE_HICACHE=1`
      - `HICACHE_RATIO=2`
      - `HICACHE_IO_BACKEND=kernel`
      - `HICACHE_STORAGE_PREFETCH_POLICY=wait_complete`
      - `HICACHE_WRITE_POLICY=write_through`
  - 是否有效：
    - **有效。**
    - 长会话 workload 中 KV cache working set 很大，单靠 GPU KV cache 容易后期崩。
    - HiCache 可以缓解 cache eviction 和长上下文压力。
    - 后续在 pruned model 上还计划测试 `HICACHE_RATIO=4`。

- **7. 修复 HiCache 触发的 SGLang/FlashInfer 启动问题**
  - 做法：
    - 分析并修复 CUDA graph padded batch size 与 FlashInfer metadata buffer size 不一致的问题。
    - 问题表现为 buffer shape mismatch，而不是普通 OOM。
  - 是否有效：
    - **有效。**
    - 修复后 HiCache 相关实验可以继续运行。
    - 该修复保证了后续服务优化实验的可执行性。

- **8. 加入 session 级准入控制**
  - 做法：
    - 在 proxy 中加入 active session 维度的控制。
    - 设置 `MAX_ACTIVE_SESSIONS=64`。
    - 将动态控制对象从 request-level inflight 改成 session-level active window。
    - 当 KV 使用率高、cache hit 下降时，暂停部分 session，而不是简单限制 HTTP 请求数。
  - 是否有效：
    - **有效。**
    - 长会话服务的主要压力来自持续活跃 session 的 KV working set。
    - session 级控制比 request 级限流更贴近问题本质。
    - 能缓解后期 cache hit 下降、TTFT 飙升和请求堆积。

- **9. 规划 KV FP8 优化**
  - 做法：
    - 在 benchmark 配置中加入 `kv_cache_dtype=fp8_e4m3`。
    - 分别测试普通模型和 pruned model 下的 KV FP8。
  - 是否有效：
    - **待完整验证。**
    - 理论上可以降低 KV cache 显存占用。
    - 但可能影响长上下文精度，因此必须绑定 RULER 等长上下文任务测试。

- **10. 设计统一 benchmark 矩阵**
  - 做法：
    - 整理了 8 组 benchmark 配置：
      - `01_dp2tp8_hicache`
      - `02_admission_dp2tp8_hicache`
      - `03_dp2tp8_hicache_kvfp8`
      - `04_admission_pruned_dp2tp8_hicache_ratio4`
      - `05_tp8_hicache`
      - `06_dp8tp8_hicache`
      - `07_admission_dp8tp8_hicache`
      - `08_admission_pruned_dp2tp8_hicache_ratio4_kvfp8`
  - 是否有效：
    - **有效。**
    - benchmark 矩阵把架构、准入控制、剪枝、HiCache、KV FP8 分开测试。
    - 有利于判断每个优化到底是否带来收益。

## 四、阶段性结论

- REAP expert 剪枝已经完成工程接入。
- 每层从 `256` 个 experts 减到 `205` 个 experts，压缩比例约 `20%`。
- `REAP + text-only` 是当前最值得继续测试的模型层优化方向。
- serving 侧最稳定的组合是：
  - `TP8 + DP2 DPA`
  - `cache-aware router`
  - `SPECULATIVE_ALGO=NONE`
  - `HiCache`
  - `session 级准入控制`
- 单纯追求更高并发或更高 DP size 不一定有效：
  - DP8 可能导致负载不均。
  - 并发过高会导致 KV cache 后期崩溃。
  - cache hit、TTFT、round latency、完成率必须一起看。
- 当前最有希望的最终方案是：
  - `REAP-20-text-only + DP2 TP8 + HiCache + active session admission`
  - 可选继续叠加 `KV FP8`，但必须先过精度验证。
